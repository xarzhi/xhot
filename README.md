# xshot

一个精简、快速的 Windows 截图工具，界面层用 **GPUI**（`gpui-kit`）构建。

```
F1                截图（可在设置里改）          F2           恢复上次贴图
Ctrl+鼠标左键拖动  直接框选并钉图，松手即完成
Enter / 双击选区   完成（动作可在设置里选）      Esc          取消
```

> 默认就是 **F1 / F2**。功能键会被系统独占，其他程序就收不到 F1 了；
> 如果不想影响别的程序，在「快捷键设置」里换成带 Ctrl / Alt 的组合键即可。
> 组合键已被别的程序占用时，那一行会标红「已被占用」。

## 功能

**截图**

- 全局快捷键或托盘菜单触发；按下时先把自己的窗口隐藏，不会拍到程序自己。
- 托盘图标**左键单击**就能截图，也可以改成打开设置面板（「常规设置」里的选项）；右键永远是菜单，
  双击也只算一次点击，不会连开两次。
- **窗口一出现就整屏变暗**，一眼看清将要框选的区域；选区内保持原亮度。
- **窗口自动识别**：还没框选时，鼠标移到任意窗口上会自动高亮该窗口的完整矩形，
  **点一下即选中整个窗口**，直接拖动则改成手绘选区。识别走窗口的 DWM 真实边界（不含投影阴影）。
- 拖拽框选，四角与四边共 **8 个锚点**可继续改尺寸；鼠标移到锚点上会变成对应的
  拉伸光标（↔ ↕ ↖↘ ↗↙）。锚点判定优先于已选中的绘制工具，所以画完图形后依然能直接拉锚点。
- 选区内的鼠标是**四向移动箭头**（拖它就是搬动整个选区），选区外仍是十字准星。
- **已画的矩形 / 圆形可以再选中并缩放**：鼠标移到图形边缘变成四向移动光标，按住可拖动；
  **单击边缘即选中该图形，四角与四边出现 8 个锚点**，拖锚点即可改图形大小（细节见下）。
- 左上角实时显示 `宽 × 高`（物理像素）。
- **取色放大镜**：还没框选区域时，鼠标右下角跟着一个浮层——以鼠标位置为中心的放大镜
  （取真实像素、最近邻放大，中心带十字准星）、当前鼠标的屏幕坐标、以及该像素的颜色值。
  颜色默认按十六进制显示，**按 Shift 在 HEX / RGB 之间切换**，
  **按 C 把当前颜色值复制到剪贴板并直接退出截图**（取色就是这一趟的全部目的，不用再按一次 Esc）。
- 双击选区内部 = 完成（即时，不受按键缓冲影响）。
- **前台窗口全屏时不截图**：「常规设置 → 全屏窗口时不截图」（默认开）会在前台窗口正好铺满整个显示器时
  （游戏、视频、演示）忽略快捷键和 Ctrl+拖动。判定用的是**客户区**和显示器矩形比（留 2 px 容差），
  并且跳过桌面、任务栏和最小化的窗口，所以"最大化"的窗口不算全屏。
- **Ctrl + 鼠标左键拖动**：无需先按快捷键，直接在任意窗口上拖一个矩形，松手就截图并钉图。
  **按下的瞬间截图窗口就出来了**（冻结画面 + 跟着鼠标生长的选框 + 取色放大镜），松手直接钉图；
  按了没移动就松开则只关窗、不钉图。这个手势用低级鼠标钩子**只观察不拦截**，被拖的窗口照常收到
  鼠标事件，拖标题栏照样能移动窗口；窗口全程**不抢焦点**（`WS_EX_NOACTIVATE`），不会打断下面的拖拽。

**标注**（工具条在选区右下角，也可用快捷键；工具条会提示当前工具的用法）

| 工具 | 快捷键 | 说明 |
| --- | --- | --- |
| 矩形 | `1` / `R` | 空心矩形 |
| 圆形 | `2` / `O` | 椭圆 |
| 箭头 | `5` / `A` | 实心箭头 |
| 铅笔 | `3` / `P` | 自由手绘，圆头笔触 |
| 马赛克 | `6` / `M` | **涂抹式**：涂到哪打到哪，可调笔刷宽度与马赛克块大小；块网格锚定屏幕坐标，多笔之间不错位，预览与成图逐块一致 |
| 橡皮 | `7` / `E` | **涂抹式**：像真橡皮一样擦到哪只消失哪一块。矩形/椭圆/箭头的边会被擦出缺口（其余边保留），铅笔笔画被切成多段，马赛克擦掉后还原原图；可调橡皮直径 |
| 文字 | `4` / `T` | 点击后输入，支持中文输入法（IME） |

- 6 种颜色、3 种线宽；橡皮提供 3 档直径（工具栏显示实际大小的圆点）；`Ctrl+Z` 撤销；再次点已选中的工具可取消选中。
- **选中马赛克或橡皮时，鼠标下会显示一个圆圈**，直径就是实际笔刷/橡皮的作用范围，涂的时候也一直跟着，
  不用靠猜。

**完成动作**

- Enter / 双击 / 工具条按钮，动作在「截图设置」里选：复制到剪贴板 / 保存到文件 / 钉在桌面。
- 剪贴板同时提供 `CF_DIBV5` + `CF_DIB` + `PNG`，粘贴兼容性好。

**长截图（滚动拼接）**

- 框好区域后点工具条上的 **长截图**（或按 `L`）：覆盖层收起成**一圈边框**（画在区域外面，还留了 3 px
  间隙，所以永远进不到成图里），只剩四条边框和工具条还是我们的窗口——
  窗口 region 被裁成那几块，于是**框内的一切点击、滚轮都归下面的程序**，而用户始终看得见正在截哪一块。
- 工具条这时只留两个按钮：**复制**（收下已拼好的图并放进剪贴板）和 **关闭**（放弃，把框选工具还回来）。
  其余按钮全部隐藏：它们要么会改动一个已经开始采集的区域，要么在采集途中没有意义。
- 之后照常滚动页面即可：后台每 120 ms 抓一次这块区域，按行签名对齐，把新出现的行拼到下面。
  一屏没动、或者内容重复（列表、表格）都不会重复拼接；看不清的跳变宁可等下一帧。
- 按 **Esc** 结束，等同于「复制」——已经滚了半天的页面，丢掉是最糟的意外。
  截图期间独占 Esc，托盘菜单里也有「结束长截图/录像」兜底。
- 选区在开始拼接的那一刻就锁住，中途不能再拖动；成图不再进保存窗口，直接进剪贴板（托盘会提示）。

**钉图**

- 尺寸严格等于截图区域（1:1 物理像素）。
- **圆角跟着截图走**：截图设置里给了圆角，钉图窗口就是同样的圆角，
  而且窗口本身是透明的——四个角后面是桌面，不是窗口自己的黑底。
- **鼠标移到识别出的文字上会变成 I 型光标**；**在文字上拖动即可选字**，松手就复制；
  单击一个字复制该词。**拖文字以外的任何地方都是移动窗口**（自己实现，不依赖系统拖拽）。
- 滚轮缩放，每格约 9%。
- **双击文字 = 选中鼠标下的那个词**（高亮，可继续右键/`Ctrl+C` 复制），**不会关闭钉图**；
  双击文字以外的区域才是「复制图像并关闭」。
- **右键菜单里的「编辑」可以继续在钉图上画**：钉图窗口向下长出 44 px 的工具条
  （矩形 / 圆形 / 箭头 / 铅笔、6 种颜色、3 种线宽、撤销、完成），框内拖拽即出图形。
  工具条长在钉图自己的窗口里，而不是再开一个窗口——钉图会被拖动、缩放、关闭，
  多一个窗口就要多跟着它跑一路。画好的图形随图像一起被复制/保存：
  坐标按钉图的对数空间保存（就是鼠标报的那个空间），落盘时才换算成图像像素，
  所以缩放过的钉图上画的线，尺寸和位置都对得上。
- 右键菜单是**独立弹出窗口**，可以超出钉图边界：复制图像 / 复制全部文字 / 编辑 / 取消·打开窗口阴影 / 保存图像至路径 / 关闭。
- 会记住上次的缩放，恢复贴图时原样还原。

**OCR 取字**

调用 **Windows 自带的 OCR 引擎**（`Windows.Media.Ocr`）：不下载模型、不增加体积，中文开箱可用。
送进引擎前会做**灰度化 + 对比度拉伸 + 2 倍放大**，屏幕上的细字识别率明显更好。
结果按**行**返回（保留引擎自己的标点与断句），选区会**补齐同一行内首尾词之间的空缺**，
所以在一行中间随便拖一下也能整句复制，不会漏掉中间的字。

**设置页（Fluent Design）**

左侧导航 + 右侧卡片，Mica 窗口材质、Fluent 2 色彩令牌、Segoe UI Variable、4px 控件圆角。

| 页面 | 内容 |
| --- | --- |
| 常规设置 | 关闭行为（最小化到托盘 / 退出程序）、保存目录（桌面 / 图片 / 下载 / 文档 / 浏览…）、完成后是否同时复制、托盘图标左键点击（截图 / 打开设置面板）、全屏窗口时不截图 |
| 外观设置 | 主题（深色 / 浅色 / 跟随系统）、钉图窗口阴影（系统中的投影） |
| 截图设置 | 完成动作、选区外遮罩浓度 |
| 快捷键设置 | 录制截图 / 恢复贴图组合键（会标出被占用的）、Ctrl+拖动开关、标注快捷键速查 |
| 关于 | logo、版本号、程序说明（版本号来自 `CARGO_PKG_VERSION`，与打包脚本、exe 属性页一致） |

**所有"从几个里选一个"的设置项都是同一个下拉**（`ui/settings.rs` 的 `setting_row_dropdown`），
用的是 **`gpui_kit::component`**——也就是随 kit 一起发布的组件库 gpui-component，它的 `Select`
自带触发器、列表、箭头、勾选、键盘和焦点环，应用这边只剩下左边的标签和宽度：
视图在 `Settings::new` 里为每个选项建一个 `SelectState`，并订阅它确认的值。
（之前用 gpui-base 那两个**不带样式的行为组件**自己拼触发器，虽然能用，但那是把库已经做好的东西又写了一遍。）

> 依赖 gpui-component 的代价是实打实的，同一台机器实测：可执行文件 **15.2 MB**、
> 安装包 **5.71 MB**、空闲内存 **35.9 MB**，对比不启用它时的 4.83 MB 安装包与 33.7 MB 内存。
> 体积能压到这个数靠的是 `lto = "fat"` + `panic = "abort"` + `image` 只留 png
> （同样带组件的情况下：23.5 MB → 15.2 MB，安装包 7.00 MB → 5.71 MB）。
> 截图那条路径不经过组件层，按 F1 到窗口出现的耗时没有变化。

## 构建运行

```powershell
cargo run            # 调试版（带控制台，便于看日志）
cargo build --release
.\target\release\xshot.exe
```

需要 Windows 10 1809+ 与 Rust 1.85+（edition 2024）。

想看每次截图慢在哪，设一个环境变量就有了（release 版同样有效）：

```powershell
$env:XSHOT_TIMING = '1'
.\target\release\xshot.exe     # 分段耗时追加到 %TEMP%\xshot-timing.log
```

## 打包安装包

用 [cargo-packager](https://github.com/crabnebula-dev/cargo-packager) 出一个
**按用户安装、不需要管理员权限**的 NSIS 安装包。一条命令就够：

```powershell
cargo install cargo-packager --locked          # 只需一次
.\target\debug\xshot.exe --export-icon assets\icon.ico   # 生成安装包用的图标（换过图标再跑）
.\package.ps1 0.2.0                            # 指定版本号打包，产物在 dist\
.\package.ps1                                  # 不加参数就沿用 Cargo.toml 里的版本
.\package.ps1 0.2.1 -SkipTests                 # 跳过测试
.\package.ps1 0.3.0 -WhatIf                     # 只看它会改什么，不动文件、不构建
```

`package.ps1` 做四件事，顺序是有讲究的：

1. **只改一处版本号**：`Cargo.toml` 里 `[package]` 段的 `version`。它不能靠"行首 `version =`"来找——
   `[dependencies.windows]` 也有一个行首的 `version = "0.62"`——所以脚本先定位 `[package]` 段再改，
   并且要求那一段里恰好只有一个 `version`。
2. **强制资源重建**：`build.rs` 用 `CARGO_PKG_VERSION` 生成 `VERSIONINFO` 资源（含 `FileVersion` /
   `ProductVersion` / `ProductName` / `FileDescription`），所以版本号会自动跟着走；脚本仍会 touch 一下
   `build.rs`，把这个"应该会重跑"变成"一定重跑了"。
3. **把版本读回来核对**：构建完直接读 `target\release\xshot.exe` 的文件属性，`FileVersion` 与
   `ProductVersion` 必须都等于要求的值，否则**直接报错并提示 `rc.exe` 不在 PATH**（Windows SDK 缺失时
   `build.rs` 只打印 warning 继续构建，那种 setup 装出来的 exe 属性里是没有版本号的——这正是脚本要拦的情况）。
4. **打包并列出产物**：`cargo packager --release`，最后打印 `dist\` 里最新几个文件、安装包自身的版本、
   以及"装出来的 `xshot.exe` 会显示哪个版本"。

版本号一共出现在四个地方，全部来自同一个 `CARGO_PKG_VERSION`，改一处就一起变：

| 位置 | 怎么来的 |
| --- | --- |
| `Cargo.toml` 的 `[package] version` | **唯一的源头**，`package.ps1` 改的就是它 |
| exe 属性页的"文件版本 / 产品版本" | `build.rs` 写的 `VERSIONINFO` 资源 |
| 设置窗口「关于」页显示的版本 | `env!("CARGO_PKG_VERSION")`，编译期常量 |
| `xshot.exe --version` 的输出 | 同上（不用开界面就能核对包装好的 exe） |
| 安装包文件名与它自己的版本 | `cargo packager` 读 `Cargo.toml` |

顺手的一点：脚本会先结束正在运行的 `xshot`（本体被占用时 cargo 无法覆盖 exe，这是实际踩过的坑）。

图标不是手画的二进制资源，而是程序画托盘图标的那段代码输出的
（`win::icon::write_ico`，16/24/32/48/64/128/256 七种尺寸），
所以托盘图标和安装包图标不可能对不上。首次打包时 cargo-packager 会自己下载 NSIS 工具链。

## 为什么是 GPUI + Win32 混合

窗口、输入、布局、矢量绘制、文字编辑全部走 GPUI。只有 UI 框架够不到的事落到 Win32：

1. **取屏幕像素** —— GDI `BitBlt`（带 `CAPTUREBLT`），整机 2560×1440 约 90–120 ms。
2. **托盘图标 + 全局热键 + 鼠标手势** —— 跑在独立线程自己的消息循环上，UI 卡住时照样可用。
3. **剪贴板位图格式** —— GPUI 只写 `PNG` 注册格式，很多软件粘不上，所以自己发 DIB。
4. **窗口移动 / 客户区精确定位** —— 无边框工具窗口在 Windows 上没有可用的系统拖拽。
5. **导出时的文字栅格化** —— 借 GDI 拿到带抗锯齿的中文。

## 实现中值得记一笔的坑

### 按下截图到窗口出现：把两件互不相干的事叠起来做

先说结论，同一台机器（2560×1440、100%）实测从按下 F1 到覆盖层画好：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 第一次截图（设置窗口开着） | ~104 ms | **55 ms** |
| 之后的每一次 | ~50 ms | **35 ms**（最好 32 ms） |

用 `XSHOT_TIMING=1` 启动就能复现：每次截图的分段耗时都会追加到
`%TEMP%\xshot-timing.log`，release 版本也有效（要测的本来就是 release）。
改之前的分段大致是：

```
2 own windows hidden  32 ms   <- 设置窗口开着时，固定 sleep 等合成器
c3 bitblt done        25 ms   <- 抓像素
open_overlay entered  12-18 ms <- 建窗口 + 建 D3D 交换链
c6 copy done           5 ms   <- 14 MB 位图拷一份给 GPUI 显示
place + foreground     2 ms
```

这里面 **抓像素** 和 **建窗口** 互不依赖，却是排队做的。现在先让工作线程开始抓，
主线程同时把窗口建出来，最后把抓到的那一帧装进去。净省下 15 ms 左右
（代价是 BitBlt 因为和建窗口抢资源慢了 2-4 ms，仍然划算）。

中间有两个坑：

1. **隐藏的 GPUI 窗口拿不到帧。** 第一版把窗口建成 `show: false`，等像素到了再
   `on_next_frame` 回调里显示它 —— 回调**永远不触发**，窗口永远不出现，日志里连
   一行都不打。gpui-pre 只为「可见」的窗口驱动帧循环（创建时那次首绘除外）。
   手动 `window.draw(cx)` 想绕过它也不行：在 `handle.update` 里面调它会撞上
   *cannot update Overlay while it is already being updated*，直接 panic。
2. 所以改成 **窗口一开始就显示，但背景透明、什么都不画**。`WindowBackgroundAppearance`
   非 `Opaque` 时清屏色是 `[0,0,0,0]`，桌面原样透出来，用户根本看不出窗口已经在了；
   像素装好后再切回不透明并画冻结帧。既没有黑闪，也不用猜显示时机。

顺带修掉的：等设置窗口消失原本是**固定 sleep 32 ms**（怕残影进截图）。
现在用 `DwmFlush()` —— 它就是「等合成器把这一帧画完」的官方原语，
一个 vsync 就够，只留 8 ms 余量，第一次截图因此少花 18 ms。

### 鼠标移到桌面上就卡：每次都把窗口列表走了一遍

「窗口自动识别」原先是在**每个鼠标事件**里调用 `window_rect_under_cursor()`：`EnumWindows`
按 z 序走一遍所有顶层窗口，命中就提前退出。鼠标停在某个窗口上时，最前面那个窗口就命中，
一两个窗口就返回了；**鼠标停在桌面上时一个都不命中，于是每一次鼠标采样都要把整台机器的
顶层窗口全走一遍**，还对其中包含该点的窗口各做一次 `DwmGetWindowAttribute`。这就是
「有窗口时正常、在桌面上就卡」的原因。

现在窗口几何被收进 `HoverIndex` 缓存起来（截图期间屏幕上的东西并不会动），
最多每 400 ms 重建一次，命中就是几条整数比较。本机实测：

```
hover index: 2 windows, build 4.71ms, 10k hits 225µs      # 每次命中约 22 ns
```

也就是每个鼠标采样从 ~4.7 ms 的 Win32 折腾降到 ~22 ns。这个「建一次、查很多次」的
比例关系由 `win::util::tests` 里的单元测试守着，免得以后又有人把枚举挪回移动路径上。

### 抓像素：从 GDI 换到 DXGI Desktop Duplication

上面那条把「抓像素」和「建窗口」叠起来做之后，抓像素就成了那条路里最大的一块。
2560×1440 实测（`cargo test --release -- --ignored --nocapture` 里的
`capture_variants` / `duplication_variant` 就是在量这个）：

| | 一次整屏抓取 |
| --- | --- |
| GDI `BitBlt`（带 `CAPTUREBLT`） | 26.5 ms |
| GDI `BitBlt`（不带） | 25.9 ms（所以慢的不是 `CAPTUREBLT`） |
| 4 线程分四条横带各抓各的 | 29.5 ms（GDI 会把回读串行化，拆线程没用） |
| **DXGI 桌面复制 → 暂存纹理 → 内存** | **2.2–2.6 ms**（`Map` 0.7 + 拷行 1.5） |

于是现在走 `win/duplication.rs`：D3D11 设备 + 每块显示器一个 `IDXGIOutputDuplication`，
拿到帧后 `CopyResource` 到暂存纹理再 `Map` 读回。约十倍于 GDI，整条路径的分段耗时里
`c2 dib allocated → c3` 从 ~33 ms 变成 **7–12 ms**。

三个必须记下来的坑：

1. **复制是「变化」，不是「画面」。** 刚创建复制对象时根本没有帧；屏幕静止时
   `AcquireNextFrame` 会返回一个 `AccumulatedFrames == 0` 的空帧（纹理是全黑的），
   而「屏幕静止」正是用户按下 F1 的典型时刻。所以 duplication.rs 自己**保存一份整屏副本**：
   每块显示器只要有新帧就刷新自己那块，没有新帧就说明那块还是副本里的样子——
   两种情况合起来都是正确答案。
2. **第一份副本只能来自 GDI**，因为上面那条。所以启动时就在后台 `warm()`：
   建好设备与复制对象，并用一次 GDI BitBlt 把副本垫上。这份开销（设备创建几十毫秒 +
   一次 26 ms 的 BitBlt）因此落在启动时，而不是落在按键那一下。
3. **GDI 仍然是兜底**，且必须留着：远程桌面、独占全屏、安全桌面下复制不可用，
   改分辨率会 `DXGI_ERROR_ACCESS_LOST`。任何一条出错就丢掉复制对象、这一次用 BitBlt，
   并顺手把刚抓到的画面 `adopt` 成新的副本。正确性有一条真实的测试守着：
   `duplication_matches_gdi` 同时用两条路各抓一次整屏逐像素比对（本机 21867 个采样点全部
   一致，最大差 1）。

换完之后整条路的样子（release、170 Hz、五次按键）：

```
0.0 ms  1 command received
0.4 ms  c2 dib allocated
7-12ms  c3 duplicated from the gpu     <- 抓像素
24 ms   c6 copy done                   <- 14 MB 拷一份给 GPUI
~30 ms  w overlay window built          <- 2) 建窗口，现在成了最大的一块
~32 ms  7 painted
```

**剩下的大头是建窗口**（16–31 ms，冷启动第一次 ~44 ms）：每次截图都新建一个 GPUI 窗口，
里面要建 Direct3D 交换链、渲染管线与文字系统。省掉它的办法是把覆盖层窗口**常驻**
（空闲时隐藏、并把它从鼠标那里彻底摘掉），按键时只装像素再显示——按上面的数字能再省
掉 15–30 ms。这条路会改动覆盖层的窗口生命周期，还没做。

### 窗口 region 用的是窗口坐标，不是客户区坐标

长截图时覆盖层只留四条边框，靠的是 `SetWindowRgn`：region 之外的部分对鼠标来说根本不存在，
所以框内归下面的程序。第一版把**客户区**坐标直接喂给了 `SetWindowRgn`，结果两条竖边怎么都画不出来
——`PtInRegion` 说它们在 region 里，`WindowFromPoint` 说那块不归我们，屏幕上什么都没有。

原因是两者差着一个**不可见边框**：即使无边框窗口也有几像素的隐形 frame（这台机器上横向 6 px），
region 要的是窗口坐标。整个 region 因此偏了 6 px：上下两条边宽 700 px，偏了照样盖住自己；
左右两条只有 4 px，偏完就落在自己 region 外面，被整个裁掉。`win::util::set_window_region`
现在用 `GetWindowRect` + `ClientToScreen` 现算这个偏移再补偿。

教训：**宽窄不同的图形会以不同的方式暴露同一个坐标错位**——一条 700×4 的边看起来"没问题"，
一条 4×580 的边就直接消失了。

### 按下就出窗口：把"建窗口"和"抓像素"都挪出关键路径

用户能感觉到的只有一件事：**按下鼠标到屏幕上出现东西**。这条路上原来有两件事，现在都不在路上了：

- **窗口不再现建**。建这个窗口（Win32 窗口 + Direct3D swapchain + 第一帧）实测约 **18 ms**，而且和
  屏幕内容毫无关系。所以它在**启动时**就建好，之后一直以隐藏状态留着，每次截图只是
  `place_client_exact`（位置没变就直接返回，省下 SetWindowPos 的 ~11 ms）+ `ShowWindow`。
  隐藏期间它不持有像素（`clear_source`），也不会吃点击（它是隐藏的）。
- **像素不再挡路**。窗口先亮起来，只画压暗和选框（`begin_capture` 把 `ready` 置 false，
  render 里没有图片可画就先不画 `img`），冻结画面落地后再叠上去——压暗已经在屏幕上，
  所以换图那一下几乎看不出来。
- **顺便**：`show_window()` 里那个 `AttachThreadInput` + `SetForegroundWindow` 也要钱（几毫秒），
  所以这条路径用 `reveal_window()`（只有 `ShowWindow`），抢前台只在真正需要键盘的截图里做。

实测（`tools/probe_drag_latency.ps1`，release，170 Hz）：

| 阶段 | 之前 | 现在 |
| --- | --- | --- |
| 按下 → 窗口已显示（`w overlay shown`） | ~40 ms | **5–12 ms** |
| 按下 → 画出"回答"的那一帧（压暗 + 选框） | 无（一直是空的） | **+0.3 ms**（`p overlay answers the press`） |
| 按下 → 冻结画面就位 | ~44 ms | 15–35 ms |

### Ctrl+拖动：截图窗口不能"抢"这次拖拽

这个手势的按下是发生在**别人的窗口**上的：钩子只观察，所以下面那个程序自己拿着这次拖拽
（`SetCapture` 在它手里）。于是有两条是不能做的：

- **窗口不能抢前台**。它一激活，下面那个窗口的拖拽就被打断；Chromium 系窗口在拖拽中被激活时
  还会把整台机器的鼠标捕获过去（就是"只有一个窗口有反应"那类症状）。所以这条路径
  `set_no_activate(OVERLAY_TITLE, true)`：显示、置顶、绘制，就是不激活。
  `tools/probe_ctrl_drag.ps1` 里"按钮还按着时前台仍是记事本"和"拖动确实移动了记事本"这两行在盯它。
- **窗口收不到鼠标事件，所以是被"告知"的**。即使它不激活，覆盖层的鼠标事件也一个都不会来
  （按下落在别人窗口上）。矩形由钩子通过 `Command::DragUpdate` 报过来（每移动 2 px 报一次，
  免得把 UI 线程叫醒太勤），窗口只负责画。工具条因此还藏起来——按不到的按钮不如不画。

另外两条是这个手势自己的规矩：

- **窗口在按下的瞬间就建好**：屏幕也是那一刻冻结的，所以框出来的画面就是用户当时看到的画面，
  而且真要用标注工具时它已经在手上。命令可能比窗口先到（甩手拖整套都在冻结画面落地前结束），
  所以"还没建窗"和"建好了但还拿着 1×1 占位图"两种情况都交给 `install_overlay` 收尾
  （`is_ready()` 判断，直接用手上那份 capture 裁切钉图，不留窗口）。
- **按了没移动就松开 = 只关窗、不钉图**。小于 8×8 视为误触，`drag_end` 直接 `cancel()`。
  否则一次误按的 Ctrl+点击会钉出一张 1×1 的图。

顺带一个环境上的坑：**光标停在管理员权限的窗口上时，普通权限进程的低级鼠标钩子根本不会被调用**
（UIPI）。所以那个窗口上这个手势不会生效，运行 xshot 的权限要和目标窗口一样。
`tools/probe_drag_points.ps1` 就是按点探测这件事的：普通窗口、Chromium 窗口、任务栏都 `saw=True`，
而本机一个管理员权限的 Qt 截图工具（PixPin）的窗口上 `saw=False`。

还有一条更早踩的坑值得留着：**抓屏之前必须等合成器换帧，不能只 `ShowWindow` 就拍**。
`ShowWindow` 是同步的，但桌面合成器手里那一帧还是旧的——第一版钉出来的整张图被压暗、还带着一圈蓝边框，
抓到的正是旧帧。`hide_window_and_wait()`（隐藏 → 轮询 `IsWindowVisible` → `DwmFlush` → 再留 8 ms）
就是为此存在的，抓屏前隐藏**我们自己的**窗口一律走它；而且要在窗口还可见时调用，
否则它会因为窗口已经不在屏幕上而直接返回、等于没等。

### 工具条用 gpui-base 的 `Toolbar`：它是行为，不是皮肤

框选区域下面那条工具条（以及长截图会话里那两个按钮的小条）现在都是 `gpui_base::Toolbar` +
`ToolbarGroup`（gpui-kit 0.7.0）。三件要知道的事：

- **它不带样式**。文档写得很直白：*the behavior primitive behind a styled toolbar*——它给的是容器、
  `Role::Toolbar` 的无障碍语义、子项之间的左右键 roving focus；背景、圆角、间距、阴影仍然是我们的，
  所以换过来之后外观没有变化。
- **id 必须在窗口内唯一且稳定**。它内部用 `window.use_keyed_state(id, …)` 保存焦点句柄，所以同一个窗口里的
  两条工具条必须是两个 id（`xshot-toolbar` / `xshot-session-toolbar`）；id 变了焦点句柄就换人，
  包含判断和按键处理都会跟着错位。
- **方向键没有被它抢走**。覆盖层用方向键微调选区（Ctrl+方向键是伸缩），而 `Toolbar` 也处理左右键——
  但它只在"焦点在它内部"时处理，而我们的按钮是普通 `div`（没有 `track_focus`），
  所以焦点始终留在覆盖层根节点。这条是**实测**的，不是推断：`tools/probe_toolbar_keys.ps1`
  先点一下工具条里的「撤销」，再按 `→`，选区左边框必须从 x=400 走到 401；哪天给按钮加上焦点，这条会立刻变红。

### 空闲的截图窗口：空着、显示着、缩到一像素

捕获窗口是**复用**的（重新建一次要 18 ms，见上一节），复用的代价是两个很具体的问题，都是踩出来的：

- **不能再隐藏它**。Windows 的合成器会记住窗口最后画的那一帧：把它隐藏再显示，屏幕上会先闪出
  上一帧——也就是**上一次的选区**（`tools/probe_flash.ps1` 用裸 DC 以约 0.1 ms 的间隔采样，
  抓到过 `firstPixel=0xE5881E`，正是 `rgb(30,136,229)` 的边框色，出现在按下后 22.6 ms）。
  所以现在它**全程显示**，空闲时被"清空"（`clear_source` + 一帧什么都不画）+ 空 region + 1×1：
  看不见、点不到、也拍不到，合成器手里留存的永远是一张空图，也就没有可闪的东西。
- **别再指望 DXGI 的第一帧**。这轮差一点把截图做成全黑：为了让空闲内存降下来，我去掉了启动预热，
  并在空闲 20 秒后释放 duplication。再看 `fill()` 就明白了——`desktop` 副本为空时会新建一张
  **全零**位图，而静止画面上监视器返回"没有新帧"，可 `capture_into` 当时对这种情况一律返回 `true`，
  于是这张黑图被当成了桌面，GDI 兜底永远轮不到。
  修法：给 `Duplicator` 加一个 `primed` 标记，只有拿到过真实画面（duplication 给了帧，或
  `adopt()` 收下了 GDI 那张）才允许用它作答；否则老实返回 `false`，让调用方走 GDI 并顺手把它喂饱。
  `tools/probe_black.ps1` 盯着这条：冻结前后同一批像素必须一致（现在是 5 个点全 diff 0）。

### 关闭窗口的手势一律放在"松开"，不是"按下"
覆盖层一开始是被鼠标**按下**关掉的（右键取消、工具条的复制/钉图/取消都一样）。这是所有麻烦的根：
窗口在按下那一刻就没了，于是配套的**松开**没人接收，Windows 就把它交给下面的窗口——
那个窗口凭空收到一次松开，当成完整点击，弹出自己的菜单（或进入别的"按下进行中"状态）。

现在**所有会结束窗口的手势都在 `on_mouse_up` 里做**，只有那个"按下"的瞬间被窗口吃掉（`stop_propagation`）：

- 覆盖层右键取消 → `on_mouse_up(Right)` 走 `back out one level`，最后 `cancel()`；
- 工具条的每个按钮、覆盖层内的双击完成、钉图的 ✕ 和双击复制关闭 —— 都是先吃掉按下，动作在松开；
- 松开落在自己的窗口上，于是**没有任何残留事件**要处理，钩子的吞事件声明在正常路径上根本不会被激活
  （日志里就是那句 `no button held, claim not armed`）。

顺带两个必须记住的细节：

- **GPUI 的 `on_mouse_up` 只对"自己处理过按下"的元素生效**。把按钮的按下监听整个删掉、只留松开，
  实测点击毫无反应（`tools/probe_toolbar_cursor.ps1` 用鼠标指针形状确认过指针确实落在按钮上：
  按钮上是手型、后面画布是十字）。所以每个"松开触发"的按钮都必须同时挂一个只做
  `stop_propagation` 的按下监听——它顺便也拦住了"按下工具栏却拉出一个新选框"。
- **关窗时不能把前台还给别的窗口**。原来的顺序是：按下 → 关窗 → `SetForegroundWindow(后面的窗口)`。
  那次激活发生在鼠标键还按着的时候，Chromium 系（VS Code 就是）会把这次激活当成"按下的开始"，
  于是自己 `SetCapture` 并把整台机器的鼠标都收走——表现就是"只有光标下那个窗口有反应，
  点任务栏都没用，再点一次右键才好"。动作挪到松开之后，激活发生在键已经抬起时，这条路自然就没了。

### 低级鼠标钩子：吃掉那一次松开

上面那条是主路，这条是兜底：万一还有哪条路径是在按下时关窗（比如长截图会话被快捷键结束、
而用户手里还按着右键），`swallow_next_button_up()` 会在钩子里记一个声明，把随后的 button-up 返回 1 吞掉。
三个细节都是踩出来的：

- **只有按着键的时候才声明**。Esc / Enter 关窗时后面没有松开事件，傻等着的声明会吃掉用户下一次点击的
  松开——那个程序就以为键还按着，左键点不动，要再点一次右键才恢复。
- **声明是认键的**。记下当时按住的是哪个键（`SWALLOW_BUTTON`），只吃那个键的松开。
- **没有时间上限**。曾经有个 400 ms 的窗口，理由听起来很合理（"松开会立刻到"），实际后果是
  **稍微按久一点的右键就把松开漏给了下面的窗口**（`probe_slow_cancel.ps1` 按住 700 ms 复现的
  就是这条）。声明在"下一次按下"时清掉、并且只吃同一个键，所以它不可能误伤后面的点击，时间限制纯属自伤。
- **`DBLCLK` 也算按下**。双击的第二次按下 Windows 发的是 `WM_*BUTTONDBLCLK` 而不是 `DOWN`。

日志写在 `%TEMP%\xshot-mouse.log`（只在声明/吃掉时写几行），真丢了点击可以从那里倒推。
`tools/probe_rmb.ps1` 盯着"右键关掉覆盖层后屏幕上不该出现任何 `#32768` 菜单窗口"，
`tools/probe_slow_cancel.ps1` 盯着慢速（按住 700 ms）右键，
`tools/probe_toolbar_release.ps1` / `probe_doubleclick.ps1` 盯着松开驱动的那几个动作确实生效。

### 关掉的窗口还压在屏幕上：`remove_window()` 只是打了个标记

GPUI 的 `Window::remove_window()` 只把 `removed = true` 记上（`gpui/src/window.rs`），真正的
Win32 窗口在 `Drop` 里才收摊，而且那里是 `ShowWindowAsync(SW_HIDE)` 外加一个 `spawn` 出去等
`when_idle()` 才 `DestroyWindow` 的任务（`gpui-pre-windows/src/window.rs`）。这中间它**还在屏幕上，
还吃点击**：覆盖层是全屏的，内容已经不再绘制，于是用户看到的景象是"点哪里都没反应"，
只有恰好点在它上面时才会被它收到。钉图、保存框、录像工具条同理，只是吃点击的范围小，
表现为"有些窗口点不动"。

所以关窗一律走 `app::retire_window()`：先用 Win32 同步 `SW_HIDE`（顺带把 region 还回去，
点击归谁是由 region 决定的），再让 toolkit 丢掉它。全屏覆盖层这一步尤其不能省，
`tools/probe_linger.ps1` 和 `tools/probe_session_exit.ps1` 就是盯着"关掉之后还有没有我们的可见窗口"。

**覆盖层是例外**：它不再被丢掉，而是隐藏并清空（`app::hide_overlay` → `hide_window_and_wait` +
`Overlay::clear_source`），因为下一个截图还要用它——重新建一次要 18 ms（见上一节）。
`probe_linger.ps1` 的输出里那条 `722642 vis=False 'xshot-overlay'` 就是它：还在，但不可见，
后面的记事本照样能拖。

### 钉图的阴影：用系统的，别自己画

钉图的投影就交给 DWM（`util::set_window_shadow` 打开 `DWMWA_NCRENDERING_POLICY`）：
系统阴影画在窗口**外面**、不占命中区域、跟着窗口走，什么都不用管。

曾经试过把它改成蓝色，结论是**不值得**：DWM 没有"阴影颜色"这种属性，要蓝色只能自己画一扇
比图片大一圈的透明窗口（负 spread 把阴影轮廓收进图片里，`WS_EX_LAYERED | WS_EX_TRANSPARENT`
让它点得透，还要在钉图每次拖动/缩放时同步、关钉图时一起关）。功能全都成立、也全都实测过，
但看起来就是不像窗口阴影——要么在图片切角处露出一圈蓝边，要么变成一圈蓝色光晕。
**已经全部删掉，回到系统阴影**；`tools/probe_shadow.ps1` 现在检查的是"钉图旁边没有第二扇窗口"。
### 单独按 Shift 是没有按键事件的

放大镜要按 Shift 切换 HEX/RGB。第一版写成在 `on_key_down` 里判断 `key == "shift"`，
真机上按 Shift 毫无反应。加日志实测：GPUI 的 Windows 后端对**单独按下的修饰键完全不派发按键事件**——
按 Shift 什么都不会来，而按住 Shift 再按 C 时，C 的事件里 `modifiers.shift` 是 `true`。
所以「按一下 Shift」这件事只能自己去问系统：`GetAsyncKeyState(VK_SHIFT)` 每 25 ms 轮询一次，
取上升沿切换，窗口关闭后任务自动退出。这是**修饰键轮询**而不是按键事件，注意别和按键路径同时处理，
否则一次按下会翻转两次。

### 橡皮只擦掉碰到的那一段

橡皮不是一个「碰到就删」的工具：删整个图形会把用户刚画好的矩形一起带走。
做法是把有轮廓的图形（矩形、椭圆、箭头）在擦除时先按 3 px 采样成折线，
再沿橡皮轨迹把被碰到的采样点摘掉，剩下的折线仍以原来的颜色和线宽画回去 ——
于是矩形的左边被擦出一个缺口，另外三条边原样保留。铅笔本就是折线，直接切；
马赛克把被擦到的采样点去掉后按原始像素重新生成，所以擦过的地方是「还原」而不是留白。

**采样是关键**：矩形轮廓本来只有 4 个顶点，橡皮擦到边中间时没有任何顶点在半径内，
切割就会原样返回、看起来毫无反应。`outline_of` 因此先把每段细分到 3 px。
图形完全没被碰到时不会被拆成折线，因此仍然保留自己的身份（八个缩放手柄照旧可用）。

### 马赛克的块网格必须锚定屏幕坐标

马赛克是按块取平均。块网格如果锚定在「当前这张位图的原点」上，
就会出现两个问题：同一张截图里的两笔马赛克各用一套网格，接缝处对不齐；
而实时预览只栅格化一小块裁剪图、导出时栅格化整张裁剪图，两者网格起点不同，
**所见与所得就不一致**。所以 `pixelate_stroke` 现在接收 `grid_origin`，
笔迹与网格统一用屏幕坐标表达，块边界一律落在 `block` 的整数倍上。


- **GPUI 在 Windows 上默认关掉最后一个窗口就退出进程**，而且会在异步任务还挂着时拆平台层直接崩。
  必须显式 `QuitMode::Explicit`。
- **`Window::remove_window()` 只是打标记**，要等 GPUI 下次处理该窗口才真正销毁。
  截图前「关掉设置窗口再等 90 ms」不够，设置窗口会被拍进图里。改用 Win32 同步 `ShowWindow(SW_HIDE)` 并轮询确认。
- **窗口矩形 ≠ 客户区矩形**：隐藏边框会让客户区比请求的小 16×8 像素，底图被拉伸、鼠标整体偏移。
  覆盖层与钉图都按客户区精确 `SetWindowPos`，渲染时再按实测比例换算坐标。
- **`start_window_move()` 在 Windows 上对无边框窗口无效**，钉图和设置窗口的拖动都是自己按光标位移移动的。
- **GPUI 的输入处理器一旦设置就不会被清除**，窗口会永久认为自己在接收文本；
  只要它这么认为，产生字符的按键（包括 Enter）就会先进 1 秒的多键消歧缓冲。
  解法是让 `accepts_text_input()` 只在文字框打开时返回 `true`。
- **`PENDING_INPUT_TIMEOUT` 是 1 秒**，所以 Enter 有约 0.4 秒延迟（单次不影响使用；要即时完成请双击选区）。
- **GDI 不写 32bpp DIB 的 alpha 字节**，截屏结果 alpha 全 0，直接给 GPUI 会整张透明。
- **GPUI 的 Windows 后端只映射了固定几种光标**，`OpenHand` / `ClosedHand` 这类会直接落到普通箭头，
  四向移动光标根本无法通过它请求。所以「可拖动」的手型/移动光标是用 Win32 `SetCursor` 自己设的，
  放在鼠标移动监听里、在工具箱处理完之后执行才能生效。
- **配置文件可能带 UTF-8 BOM**（很多 Windows 工具会写），读的时候要剥掉，否则 serde 解析失败并静默回退默认值。

## 已知限制

- **全局组合键被占用时不会抢占**：Windows 只允许一个程序拥有某个组合键。
  默认的 `F1` / `F2` 在已经装了其他截图工具的机器上可能被占用，
  此时「快捷键设置」页会标红「已被占用」，换一个即可（托盘菜单始终可用）。
- **裸功能键会被系统独占**：`F1` 按下后其他程序收不到。要避免这一点，
  在「快捷键设置」里录一个带 Ctrl / Alt 的组合键。
- **Enter 有约 0.4 秒延迟**，来自上面那条 GPUI 的按键缓冲；双击选区或工具条按钮是即时的。
- **混合 DPI 多显示器**下覆盖层按主显示器缩放比铺满虚拟桌面，不同缩放比的副屏上可能有极小像素误差。
- 文字提取依赖系统已安装 OCR 语言包；没有安装时钉图仍可用，只是没有可选文字。
